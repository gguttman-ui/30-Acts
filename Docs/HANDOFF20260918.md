## 1. The one that matters most: production OTAs were firing on every push

`.eas/workflows/publish-update.yml` ran `on: push: branches: ['main']` and
published an over-the-air update to the **production** channel - the channel the
App Store build reads, with no review and no gate.

This had been live since at least August. The commits that triggered it tell the
story:

- "Docs: add backlog item 25, Twilio HELP auto-repl..."
- "Docs: add backlog items 23 and 24, sync repo c..." (twice)
- "Ignore database backups containing user data"
- "Stop tracking database backups containing user..."

Editing a markdown file shipped JavaScript to users.

**Fixed** (commit `48c0a4e`): push trigger removed, `workflow_dispatch` only.
Verified by pushing four days of commits afterwards - no run started. Pushed
again later, still nothing.

Also stale: the workflow's hardcoded update message,
`OTA - grid fit, tile glyph, Phone label wrap`, which every production update
carried regardless of content. Publish deliberately from the CLI instead so the
message is real.

**This leaves an open question for release day - backlog item 36.** Pressing
Release This Version gives users the approved binary PLUS whatever sits on the
production channel at that moment. Today that is the OTA from 14 Sep
(`12f7fcf`), which is neither the code the binary was reviewed with nor current
main. Decide it deliberately.

## 2. Supabase storage was open to the world

Four policies on `storage.objects`, named "act-media demo: anyone can ...",
granted the **public** role SELECT, INSERT, UPDATE and DELETE on the `act-media`
bucket. Anyone holding the anon key - which ships inside the app binary, sits in
`eas.json`, and has been in the GitHub repo - could list, overwrite or delete
every act photo and share card.

Live from early development until 17 Sep.

**Production:** all four dropped. Emailed share cards still render, because the
bucket's `public` flag serves reads without consulting RLS - that was checked
before and after with a real card URL, not assumed.

**Staging:** had no bucket at all. Created 17 Sep with authenticated-only INSERT
and SELECT from the start, so it never had the hole.

Left alone deliberately: `file_size_limit` and `allowed_mime_types` are null on
both, so any signed-in account can upload any file of any size. Backlog item 31.

Checked while there: the app only ever calls `upload()` with `upsert: false` and
`getPublicUrl()`. No `.remove()`, no `.update()`, no `.list()`. Dropping the
write policies broke nothing.

## 3. App Store privacy answers corrected

The declaration was missing what Branch collects. Added, live, no build needed:

- **Identifiers -> Device ID** - App Functionality, linked, **not** tracking
- **Usage Data -> Product Interaction** - same answers

Tracking stays **No** on both. A Yes would oblige an App Tracking Transparency
prompt the app does not have, and Branch is used for deferred deep linking, not
paid ad attribution.

Declined deliberately: Browsing History and Other Data, which Branch also lists.
Over-declaring is safe with Apple but those appear on the public product page,
and "Browsing History" under a kindness app reads worse than it is.

Already correct, and worth knowing: **Photos or Videos was never declared**, so
nothing there needed fixing.

`react-native-branch` is at 6.8.0, which ships Apple's required privacy
manifest, so the SDK side was fine.

## 6. Backlog items done

### Item 30 - one source for the Supabase project (commit `10382ce`)

Five files each carried their own copy of the `EXPO_PUBLIC_SUPABASE_*` lines,
**every one falling back to PRODUCTION**. That is what let a staging build write
to live data on 16 Sep with nothing on screen saying so.

- New pure module `src/lib/supabaseEnv.js` is now the only place those vars are
  read. `supabase.js` re-exports, so existing imports still work.
- The fallback is **staging**, never production, and warns when it fires.
- Settings shows a second line - `db - staging` or `db - production` - read off
  the Supabase URL the app actually holds, **not** the build channel. The two
  disagreed on 16 Sep and nothing said so.

Verified on device: update `01a0b5ac`, `db - staging`.

The module is deliberately pure - no AsyncStorage, no supabase-js - because
importing the client into `moderation.js` broke 44 tests. Same lesson as
`dashboardPages.js` yesterday.

### Item 35 - iOS autofill on sign-up (from Bridget)

Bridget asked why the app cannot take the phone number from the phone. **It
cannot** - iOS gives no app its own number, and no amount of wanting changes
that. But it can let iOS offer the saved number for one tap, and the app was not
asking it to.

`textContentType` / `autoComplete` added to Mobile Number, First Name, Last Name
and ZIP. The trap: `AppInput` destructures a fixed prop list, so the hints were
being dropped - adding them at the call sites alone would have looked like iOS
simply not offering. `AppInput` now forwards them.

Caller ID blocking is irrelevant here - it affects outbound calls only.

### Item 11 - Sentry app hang "false positives", confirmed false

REACT-NATIVE-6 ("App hanging between 85.4 and 86.2 seconds") and REACT-NATIVE-7
(OS watchdog terminated the app). 3 events, 1 user, iPhone SE 3rd gen, build
1.0.0 (96), all around 1 Sep, nothing since.

**The session replay settled it**: the screen was
`MFMailComposeInternalViewController` - Apple's mail compose sheet, raised when
someone taps Email to share an act. A tester spent 85 seconds writing an email.
The stack agreed: the main thread was parked in `mach_msg2_trap`, which is an
idle run loop, not blocked code.

`enableAppHangTracking: false` in `Sentry.init`, with the reasoning in a comment
there. It would only have got worse with real users - every slow email is an
event against a finite quota. Accepted cost: a genuine freeze is no longer
reported as a hang. Crashes and JS errors are unaffected.

`replaysOnErrorSampleRate: 1` is what made this diagnosable. Leave it alone.

`ShareRow.js` deleted; leftover share styles stripped from four screens. 61
deletions, 0 insertions, 298 tests still passing.

## 7. Item 26 prepared, not yet built

Switching between staging and production meant deleting the app and reinstalling
from a QR code, because both shared one bundle identifier. That is a permanent
tax, not a launch-week annoyance, so it was brought forward.

`app.config.js` now exists. **`app.json` is still the only description of the
production app** - the config function returns it untouched unless
`APP_VARIANT=staging`. Production cannot drift because nothing on the production
path modifies anything.

Staging gets: `org.30actsofkindness.app.staging`, name "30 Acts (Staging)",
display name "30 Acts Stg", scheme `thirtyactsstg`, an icon with a red STAGING
band, and **empty `associatedDomains`** so it never competes with production for
Branch universal links.

Unchanged in both: `slug`, EAS `projectId`, updates URL, `runtimeVersion`, every
plugin. Keeping the project id is what lets `eas update --branch preview` still
reach the staging app.

**Proven, not asserted:** `config-baseline.json` was captured before
`app.config.js` existed; `Compare-Object` against it afterwards returned nothing.
Do that check again before any production build:

```
npx expo config --type public | Out-File -Encoding utf8 config-check.json
Compare-Object (Get-Content config-baseline.json) (Get-Content config-check.json)
```

Commit `9856719`. **Next step is one command:**

```
eas build --profile preview --platform ios
```

Then install it and confirm "30 Acts" and "30 Acts Stg" sit side by side.

Two notes: clear `$env:APP_VARIANT` after any staging config check, or later
