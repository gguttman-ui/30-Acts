## Unplanned: production Disk IO

Supabase emailed at 00:20 that production (`mtfyekdxtkdiaqbgaoza`) was
depleting its Disk IO Budget. A database of 57 MB with fifteen users should not
be doing that, so it was worth stopping for. It turned out to be **two
independent causes**, both real, and **neither** caused by anything changed
recently — the compute chart is flat from 13 September, with no step at the
7pm `is_admin()` change.

### Cause 1 — the instance was too small

`t4g.nano`: 0.5 GB RAM, 5 MB/s sustained throughput. Memory commitment was
**1.35 GB** against 0.5 GB of RAM, so it swapped continuously, and swap traffic
*is* disk IO. Nothing about the data was causing it.

**Fixed:** upgraded Nano → Small — 2 GB RAM, 22 MB/s, 90 connections instead of
60. **+$5.15/month** ($9.68 → $14.83). The database restarted; the production
app reconnected cleanly and felt marginally faster.

### Cause 2 — pg_net's response table was 120× bloated

`net._http_response` held **72 live rows in 16 MB**. pg_net inserts a row per
HTTP call and deletes it shortly after, so the table churns hard; dead rows had
outrun autovacuum. pg_net's own cleanup worker then rescanned that bloated heap
constantly — **43% of all query time, 1h 2m in 24 hours**, on top of two
`net.http_post` entries worth another 34 minutes.

The 99.99% cache hit rate is the tell that this was never about user queries.

**Fixed:** `vacuum full net._http_response` → **16 MB to 136 kB**.

Autovacuum could not be tuned on it — `ALTER TABLE` fails with *must be owner
of table*, since the `net` schema isn't ours. (Curiously, `VACUUM` is allowed
but `ALTER` is not; Supabase grants maintenance rights without ownership.) So
instead, **cron job 14 `vacuum-net-http-response`** runs plain
`vacuum (analyze)` hourly at :17, deliberately off the reminder job's
five-minute cadence. Plain vacuum, not full — no exclusive lock, and it keeps
space reusable so the table stays flat.

### What was checked and found clean

- `net.http_request_queue` — 0 rows, 40 kB.
- `cron.job_run_details` — already pruned to 7 days by job 8.
- **Staging** — `net._http_response` is 0 rows, 32 kB.

That last one raises a question for **item 16 (volume and load testing)**:
staging appears not to run the same cron jobs as production, so load testing
there would not be like-for-like. Worth establishing before that work, not
during it.

### Result and what to check

Disk IO fell **46% → 29%** within the hour, on a 24-hour average still carrying
the pre-fix hours. **Check it again tomorrow.** If it hasn't kept falling well
below that, something else is going on and it needs another look.

## Found on the way — a credential in the clear

Job 7 embeds the **service_role secret key in plaintext** in its command text,
as both the `apikey` and the Bearer token. Anyone who can read `cron.job` sees
it, and that key bypasses RLS entirely.

It is not a public leak — it needs database or dashboard access — but the
organisation has members, and rotating a service_role key after it has spread
is far more painful than moving it now. The standard fix is Supabase Vault:
store the key there, have the cron command read it, so the secret never appears
in `cron.job.command`. Then rotate, on the assumption it may have been seen.

Logged as **backlog item 45**, priority 1, before first real users. Of
everything on the list, this is the one I would not leave long.

## 1. Create Group was a dead end

Settings > "Sponsor a New Group" opened a screen with no back arrow and no
cancel. Tap it by accident and the only way out was to kill the app.

`CreateSponsor` is registered bare in the stack, which sets
`headerShown: false` for everything, and `CreateSponsorScreen` renders no
header of its own — just a plain `<Text>` title. Its two siblings,
`MySponsorsScreen` and `JoinSponsorScreen`, both render a `ScreenHeader` with
an `onBack`. It was the odd one out.

**Fixed at the navigator**, not in the screen: `headerShown: true` plus a
`headerLeft` that calls `goBack()`, the same shape `SponsorDetail` already
used. One change, and because it is the stack header it covers both of the
screen's views — the form and the post-create QR screen.

**Why not the shared `ScreenHeader`:** that screen's body is white (`#fff`)
while the rest of the app is the dark `C` palette, and `ScreenHeader`'s title
colour is `C.text` (`#e8f5e9`) — invisible on white. Restyling a 455-line
screen eleven days out was not worth it. Logged as **item 49** instead.

## 2. Restart Challenge did nothing

The confirm dialog appeared, "Yes, restart" was tapped, and the old streak came
straight back on the next load.

Not a logic bug — a **broken wire**. `onRestart` is threaded
`App.js -> AppNavigator -> MainTabs` and handed to `HomeScreen`, but
`renderSettings` never passed it on, and `SettingsScreen`'s props signature did
not name it. So the dialog fell through to `onStartChallenge`, which is only
`await reloadDays()`. `profiles.last_restart_at` was never written.

`App.handleRestart` itself was correct the whole time.

Three lines: pass it in `renderSettings`, accept it in the signature, call it
from the dialog.

Restart is the only wipe mechanism in the app, so this was silent — nothing on
screen said the request had been dropped.

## 3. Found on the way — a production build would have pointed at staging

This one was not reported by anyone and matters more than the two that were.

Gary's instinct, before the OTA, was that `supabaseEnv.js`'s fallback should
point at production rather than staging. Looking at it, the fallback was not
the problem — **`eas.json` was**. The `preview` profile set
`EXPO_PUBLIC_SUPABASE_URL` and `_ANON_KEY` explicitly. The `production` profile
set **neither**.

`EXPO_PUBLIC_*` values are inlined from the build profile at bundle time, so a
production build got `undefined` for both, fell through to the fallback, and
pointed at **staging**.

Flipping the fallback would have papered over that while re-arming the failure
documented on 16 Sep — a preview build silently writing to live data. So both
profiles now name their database explicitly, and the fallback stays pointed at
staging, which is the harmless direction for a misconfigured build.

**Build 98 is unaffected.** It was built 11 Sep; `supabaseEnv.js` was not
created until 18 Sep, so build 98 still carries the old per-file production
values. Worth confirming rather than trusting the dates — its Admin page should
*not* read 999,999.

## Shipped to staging

`eas update --branch preview --environment preview --platform ios`, update
`01a0c149`, group `8eecf774-5ac9-42d2-9cb8-9ce306f49569`.

Gary confirmed both fixes on device, including that the restart persists across
a force-quit.

**The first attempt died** with `FATAL ERROR: AlignedAlloc Allocation failed -
process out of memory`. The export defaults to `--platform=all`, bundling iOS,
Android and Web in one Node process against a ~370 MB heap ceiling. Fixed with:

```powershell
$env:NODE_OPTIONS = "--max-old-space-size=8192"
npx eas update --branch preview --environment preview --platform ios -m '...'
$env:NODE_OPTIONS = ""
```

`--platform ios` is the real win — Android and Web are not shipped, so
two-thirds of that work was wasted. Clear `NODE_OPTIONS` afterwards or later
commands in that shell inherit it.
