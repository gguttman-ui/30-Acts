## The 1 October decision, settled

**Release build 98 as approved, and OTA the fixes. Do not rebuild first.**

The constraint that decided it: swapping the build on version 1.0 returns the
version to review — the same mechanism as the "cancel this release" button. So
there is no way to hold 98's approval in reserve while trying for another. A
rebuild spends an approval already in hand, in a queue that has rejected this
app twice.

The asymmetry: the OTA path's worst case is a rough edge for one session,
patchable the same day. A rebuild's worst case is missing 1 October entirely.

**What 27 and 28 do on launch day.** Both ship with the 1 October OTA rather
than waiting, at Gary's decision. Worth being precise about how they travel,
because they are not the same:

- `send-reminders` is an **Edge Function** — it is not inside the app at all.
  Deploying it changes behaviour for every user on every version, instantly.
- The Settings card is **JavaScript** — it reaches build 98 by OTA.

Deploy the two together. Backend alone means people see two reminder slots but
only ever get one text; app alone means the screen shows one reminder while the
server would still send a second to anyone who had one set.

### The gap that cannot be closed by OTA

Every new download runs build 98's **embedded** JavaScript for its entire first
session. The OTA downloads during that session and applies on the next launch.

This was checked, not assumed, and twice: `app.json`'s `updates` block carries
only a `url`, so the default applies (launch on the embedded bundle, fetch in
the background) — and that setting is baked into the binary, so it cannot be
changed by OTA. Separately, `expo-updates` appears in the app's own code only to
print the build stamp in Settings; there is no `checkForUpdateAsync` and no
`reloadAsync`, so nothing self-corrects mid-session.

So a public user who signs up on 1 October gets, in their first session only:
the Create Group screen with no back arrow, the old two-reminder card, and a
Restart that does nothing. Of those, only the first is likely to be hit — Gary
expects group creation to be common early, and backing out of that form traps
them until they force-quit. Restart is near-zero risk; nobody restarts on day
one.

### Why 1.0.1 should follow immediately

The gap above recurs for **every** new download until a new binary is in the
store. It is not a window that closes on 1 October.

You cannot prepare 1.0.1 while 1.0 sits unreleased, so the sequence is forced:
press Release on 1 October, then submit 1.0.1 the same day.

**The fact that resolves the worry:** phased release only throttles automatic
updates to people who *already* have the app. It does not hold back new
downloads — the App Store always serves a new customer the newest approved
version. So the moment 1.0.1 is approved, the first-session gap stops affecting
new public signups entirely, phasing or not. The exposure is the few days
between release and approval; the last review took four.

This also lines up with the runtime fork being cheapest while the user base is
smallest. `runtimeVersion` follows `appVersion`, so 1.0.1 splits the OTA
audience — every later OTA must go to both runtimes or the people still on 1.0.0
quietly stop receiving fixes. At 50–100 users that tail is trivial. At 500 it is
not.

## Items 27 and 28 — built, staging only

Both written, tested, committed to the working tree, and deployed to **staging**.
Nothing on production.

**Item 28, one reminder a day.** The slot-2 block is gone from `send-reminders`
and the second control is out of the Settings card. `handleSave` still writes
`reminder2_*` as nulls — deliberately, because there is no UI left to clear a
schedule someone already had, and stale live-looking values are how a future
change quietly resurrects a feature.

**Item 27, the inactivity cutoff.** Phones with a completion inside the window
load once per run into a Set, the same shape as `loadOptOuts`. A per-user query
would have multiplied the query count by the whole user base on every
five-minute tick, and that function already walks every user.

Three details that are load-bearing:

1. **`loadActivePhones` returns `null`, not an empty Set, on error**, and the
   caller then skips the check entirely. An empty Set would make every user look
   inactive — one transient query failure would text the entire user base a
   shutoff notice and disable everyone's reminders, with no way afterwards to
   reconstruct who had chosen what.
2. **Accounts that never completed an act are measured from `created_at`**, so a
   new signup gets ten days of grace rather than being shut off before they
   begin.
3. **The window is computed eleven days wide, not ten.** `local_date` is a local
   calendar date and can sit either side of UTC; erring wide means the worst
   case is one extra reminder, never an early cutoff.

### Verified on staging

## Tests, and one that tests nothing

Three new files yesterday, one today (`__tests__/reminderPolicy.test.js`). Each
was run **both ways** — against the change and against a reconstructed
pre-change copy — to confirm it fails on the bug it was written for. For the
reminder work: 22 pass after, 8 fail before.

`reminderPolicy.test.js` also does something the other suites don't: it extracts
the real SMS string literals and checks them for ASCII and length. That is the
trap that actually costs money — one curly quote or em dash flips a message from
GSM-7 to Unicode and cuts the segment from 160 characters to 70.

**Worth recording as a lesson.** The first version of the fail-safe assertion
matched loosely from `if (error)` and ran on to the function's own successful
`return set`, so it passed whether or not the fail-safe existed. It only showed
up because it failed for an unrelated reason. A source assertion that is too
loose does not weaken a test — it silently removes it.
