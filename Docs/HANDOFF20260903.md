## Code changes since the last handoff

All on `preview`, all included in build 97.

### 1. The content filter now runs where people actually write

`isContentBlocked` guarded `DailyActScreen` and the display name, but **not
`MyStoryScreen`** — the screen everyone uses. The main user-authored field in
the app was going into the database unscreened while the review notes were
about to tell Apple that submitted text is filtered.

Added to `MyStoryScreen`, `CreateNewActScreen` and `SuggestActScreen`.
`__tests__/moderationCoverage.test.js` fails if any screen that stores typed
text stops calling it.

### 2. …and then the filter had to be fixed, because it was rejecting kindness

Every banned word was matched as a plain substring. Tolerable on the retired
DailyAct path; a serious defect once it screened every story. Real examples it
blocked:

| Story | Blocked by |
|---|---|
| I bought **grapes** for my neighbour | `rape` |
| I changed my at**tit**ude and apologised | `tit` |
| I signed a pe**tit**ion for the food bank | `tit` |
| I read **Dick**ens to my grandmother | `dick` |
| I fed the pea**cock** at the sanctuary | `cock` |

`src/lib/moderation.js` now splits the list in two. **Stems** that occur inside
no innocent English word (`fuck`, `masturbat`, `porn`…) still match anywhere,
so inflections need no listing. **Whole words** that do occur inside innocent
ones (`tit`, `rape`, `cock`, `ass`, `dick`…) match only on word boundaries plus
normal suffixes — so "tits" is caught and "attitude" is not.

`breast` came off the list entirely. "I walked for breast cancer research" is a
plausible act of kindness, and blocking it is worse than anything the word
could cost.

Verified against all 183 catalogue acts plus 24 realistic stories.
`__tests__/moderationWordlist.test.js` holds those, and 17 that must still be
blocked.

**A false positive here is worse than a false negative.** Stories are private,
and anything that could reach another person is human-approved first. Keep that
in mind before adding words.

### 3. The bracelet was quoted at two different prices

`RecognitionScreen` advertised "$4.95 shipping & handling". The address form,
the payment screen and the amount actually charged were all **$6.95**. Someone
choosing the bracelet was quoted one price and asked for another two screens
later — and the review notes said $6.95, so a reviewer following that flow
would have seen the mismatch.

Fixed, with `__tests__/braceletPrice.test.js` failing if those three screens
ever disagree again.

## What to do while you wait

### The staging database — the one real piece of work

This is the long pole and review is dead time. Everything is already written:
`Docs/SUPABASE-STAGING-SETUP-20260828.md` and `Desktop\staging-setup.ps1`.

**Why it matters:** every tester build and the App Store build currently talk to
the same Supabase project. Fine while it is you and David. The day real people
sign up, a tester completing acts writes rows your growth metrics count, a
tester triggering reminders sends **real SMS to real numbers**, and a bad
migration is tested against your users' data.

**The good news** is that pointing testers elsewhere is an `eas.json` change,
not a code change — the app already reads its connection from environment
variables with the live project only as a fallback.

**The single riskiest mistake**, called out in the setup doc: a staging
`pg_cron` job still pointed at the production Edge Function URL would send real
SMS from your test environment. Check every cron URL after cloning.

It needs a new build to take effect, since env vars are baked in at build time.
That is fine — it pairs with the Sentry change below.

### Staging — started 3 Sept, PAUSED mid-way by choice

Resume after Apple approves. Nothing is half-broken; the staging project is
empty and costs nothing sitting there.

**Done:**

- `30-acts-staging` created — ref `rhalruwxylggkrebyesf`, West US (Oregon),
  Free, in the **gmail** org alongside production. Automatic RLS left on.
- PostgreSQL 17 client tools installed on the laptop
  (`C:\Program Files\PostgreSQL\17\bin`; add to PATH per session with
  `$env:Path += ";C:\Program Files\PostgreSQL\17\bin"`).
- `supabase\` folder created in the repo.

**Stopped at:** dumping production's schema. It needs the production database
password, which nobody had, and resetting it means touching production while a
reviewer may be using the app. Gary chose to wait. Correct call — the reset is
safe (the app authenticates with the publishable key, never this password), but
there is no reason to take even a small risk during review.

**To resume, in order:**

1. Settings → Database → **Reset database password**. Avoid `@ : / # ? % $` in
   it — those break the URL format.
2. Connect → Direct connection string → **Session pooler** → URI. Paste it into
   Notepad, replace `[YOUR-PASSWORD]`.
3. In PowerShell, from the repo:
   ```powershell
   $env:Path += ";C:\Program Files\PostgreSQL\17\bin"
   $conn = Read-Host "Paste connection string"     # right-click pastes; Ctrl+V does not
   pg_dump --schema-only --no-owner --no-privileges -d $conn -f supabase\prod-schema.sql
   ```
4. Check the file has `CREATE TABLE` and `CREATE POLICY` lines and **no**
   `INSERT INTO` — that is the check that no user data is riding along.
5. Paste it into the staging project's SQL Editor and run it.
6. Then steps 3–9 of `SUPABASE-STAGING-SETUP-20260828.md`: auth settings, Edge
   Functions, cron, seed data, `eas.json`.

**Why not the Supabase CLI:** `supabase db dump` shells out to Docker, and
Docker Desktop is not installed. `pg_dump` direct avoids that entirely.

**Do not copy user data.** Schema only, then seed fake accounts in the
`555-010-xxxx` range. Real phone numbers in a database that has reminder cron
jobs would send real SMS to real people — the worst failure mode in this whole
exercise.

### Backups — this is why production should go Pro after launch

The empty project said "Last backup: 4 hours ago". The database holding your
restored thirty days and every user's stories says **"No backups"**. Free tier
does not back up; Pro gives daily backups with 7-day retention.

So the same $28.75 that was protecting an empty schema should, after launch,
protect the database that actually holds something. Not before — there is
nothing to lose yet. This answers backlog item 8.

### Sentry environments — small, and worth it on launch day

`Sentry.init` in `App.js` sets no `environment`, so **every preview build
reports as `production`.** Both app-hang alerts this week came from preview
builds and looked like production incidents. Once real users exist you cannot
tell whose error is whose. Set it from the channel at init; it needs the same
new build as staging.

## Three things App Store Connect sprang on us at the end

Recorded so version 1.1 is not a surprise:

1. **A price tier must be set** before *Add for Review* will work at all, even
   for a free app.
2. **A regulated-medical-device declaration** is required — answer No. It is
   triggered by the Health & Fitness category. **Lifestyle** describes the app
   better and avoids this class of question; changeable any time on the App
   Information page.
3. **The Build section does not appear** on the version page until a binary has
   been uploaded, which makes the order of steps confusing. Run
   `eas submit` first, wait for Apple's processing email, then attach it.
