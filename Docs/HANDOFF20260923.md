## Tomorrow: volume testing (item 16) - thoughts to study tonight

### Two questions only you can answer

1. **How many people, and how fast?** Rough guesses are fine: sign-ups on day 1, sign-ups in week 1, and how they arrive. A launch email sent at one moment makes a burst; a talk or event where a room signs up together on the same Wi-Fi makes a sharper burst from ONE internet address.
2. **When will reminders fire?** The reminder time defaults to 9:00 AM. If most people keep the default, every reminder in a time zone is due in the same five-minute tick. That is the single most likely thing to break.

### What could break, most likely first

| # | Risk | Why | How we test it |
|---|---|---|---|
| A | **Reminders at 9:00 AM** | One `send-reminders` run every 5 minutes handles everyone who is due, texting them one after another. It already takes over 5 seconds with nothing to send. Edge Functions have a time limit per run; if 1,000 people are due at 9:00, the run may not finish and the rest never get their text (the idempotency table stops duplicates, not misses). | Seed N fake users on staging all due at the same minute, with staging switched to **Twilio test credentials** (no real texts, no cost). Invoke once; record duration, `sent`, `errors`. Repeat at 100, 500, 2,000. |
| B | **Sign-up burst** | Supabase Auth has per-address rate limits on sign-ups and sign-ins; Twilio Verify limits sends per number (we hit ~5 per 10 minutes today); our new hook adds a lookup per sign-in. A room on one Wi-Fi could hit the per-address limit. | Read the Auth rate-limit settings in the dashboard (no need to hammer anything) and decide whether to raise them for launch. |
| C | **Everyday app traffic** | Many people logging acts and loading the dashboard at once. Staging is on Free/Nano - smaller than production (Pro/Micro) - so staging results are the pessimistic case. | A small Node script (the repo already has `@supabase/supabase-js`) that signs in N fake users and has each log an act and load the dashboard, run from the laptop. Watch the Supabase report pages (CPU, disk IO, response times). |
| D | **Big trees** | `get_tree_stats` now walks the whole downline (item 57). | Seed a chain of ~1,000 with branching and time one call. |
| E | **Disk IO budget** | Supabase warned about disk IO on 12 Sep (write load, cron churn). | Watch the IO chart during C. |

### Guardrails for the session

- **Staging only.** Nothing touches production.
- **Twilio test credentials on staging for the whole session**, switched back at the end. Twilio's test numbers accept messages without sending or charging. This is the one step that stops a load test from texting real people.
- Fake users are clearly marked (a fixed fake phone range and a marker in the name) so one query finds and deletes them.
- **Snapshot and fingerprint first, restore and compare at the end** - the `snap_17` method proven today.
- One step at a time, each with its result, as usual.

### What we come away with

A number for each risk and a decision: fine as is / fix before 1 Oct / fix after launch. The most likely "fix before" is A - for example spreading `send-reminders` across several parallel runs, or sending in batches.

## Lessons from today worth keeping

- **Audit the database, not just the app.** One query found every `security definer` function the public key could run (`pg_proc`, `prosecdef`, `has_function_privilege('anon', ...)`); a second read the actual policy rules (`pg_policies.qual`). Policy NAMES lie ("Service role full access" applied to everyone).
- **Secrets hide in function bodies.** Two Twilio tokens (one dead, one live) and a Resend key were written into SQL functions. Everything now reads Vault. Search: `prosrc ~ 'AC[0-9a-f]{32}:[0-9a-f]{32}'`.
- **Fingerprints prove identity without revealing a secret** - sha256 in SQL matched against `supabase secrets list` digests.
- **A PL/pgSQL function is not checked until it runs.** "Installed" proves nothing; end every install with a real call.
- **A recursive query may refer to itself only once** - combine the sources first (`members` CTE).
- **The SQL Editor shows only the last statement's result.** Put the check last.
- **Snapshot-and-restore works:** copy tables to a `snap_` schema, fingerprint, test, restore with `session_replication_role = replica` and a column list that skips generated columns, compare fingerprints, drop the schema.
- **File writes to the laptop can land one version behind.** Re-read (size or compare) after every write; a second write pushed it through each time.
- **Clipboard trap:** pasting a command into PowerShell replaces what was copied. Use the `Read-Host 'Copy ... then press Enter'` pause.
- **Twilio Verify:** texts to Google Voice numbers do not arrive (calls do); about 5 sends per number per 10 minutes.

## Standing rules

- One step at a time, each with an explicit verification. Every step says where it runs: **SQL Editor (staging/production)**, **PowerShell**, **dashboard**, or **iPhone**.
- After each testing set, show both lists; keep list 2's "Waiting deployment" column, waiting items at the end.
- No placeholder text in commands. Never paste secrets into chat.
- `||` avoided in the SQL Editor; use `concat()`.
- Never publish to `--branch production` until Release This Version is pressed; always pass `--environment`.
- Database dumps and snapshots stay out of the repo.
- Watch what `git add -A` sweeps up - add files by name.
- Re-stage a file from the laptop immediately before reading it; re-read it after writing it.
- **New:** from 30 Oct, a new table in `public` needs explicit `grant` statements (Supabase change). Write grants deliberately with every new table.
- **New:** do not test deletion on production.
