## Two defects found in testing, both fixed

Neither could have been caught by the test suite, and that is the point.

### The shutoff row was being rejected

`SHUTOFF_SLOT` was 0. `reminder_sends` carries

```
CHECK (slot = ANY (ARRAY[1, 2]))
```

from when slots 1 and 2 were the only things recorded there. Every shutoff
insert was rejected.

The visible behaviour was fine — text sent, reminders disabled — so the test
"passed" while the idempotency guard did nothing at all. In production that
would have left one safeguard doing the work of two: if `disableReminders` ever
failed, the person would be texted every day with nothing to stop it.

**Fixed:** `SHUTOFF_SLOT = 1`, sharing the slot with the real reminder. That is
also better behaviour — if a reminder already went out today, the already-sent
check short-circuits before the inactivity check, so the shutoff waits until
tomorrow instead of landing as a second text the same day. `status` is what
tells the two apart (`shutoff_notice` vs `sent`).

Rejected the alternative — widening the constraint to allow 0 — because it means
a schema change on two projects nine days from launch, and staging and
production have drifted before (`confirm_phone_users`).

### The rejection was invisible

`recordSend` discarded its insert result. supabase-js **returns** errors rather
than throwing, so the failure never surfaced.

**Fixed:** it now destructures the error and `console.error`s it, with the
reason in a comment. A test asserts the check is there, so it cannot be quietly
removed.

**Backlog item 51 added**: `recordOptOut` and `disableReminders` still discard
their errors, three more call sites of the same bug. `disableReminders` is the
serious one — a silent failure there after the text has gone out means the
person keeps their schedule and gets texted again tomorrow.

## How half an hour got lost, and what to do differently

Worth recording, because it will happen again otherwise.

**My file writes were landing a version behind all morning.** The file on disk
would still hold the previous version after a write reported success, and my
view of the disk lagged too — so I twice read state that was not current and
reasoned from it. That produced two wrong theories about why the row was
missing, and a deploy that shipped the unfixed code while everyone believed
otherwise.

**What actually worked:** reading the file through Gary's own shell.

```powershell
Select-String -Path supabase\functions\send-reminders\index.ts -Pattern 'SHUTOFF_SLOT = '
```

**The rule for next time:** after any file is written and before it is deployed,
read it back through PowerShell. Do not trust a write that reported success, and
do not trust my view of the disk. `npm test` serves the same purpose for test
files — the test count is the tell (342 vs 343 told us exactly which version had
landed).

A second, smaller trap: a `supabase functions deploy` block in scrollback looks
identical to a fresh one. A deploy was read as having run when it had not.

The related lesson is the one item 13 already cost a day for: when a fix reasoned
from code does not work, stop and get evidence. Reproducing the failing insert
directly in SQL — which succeeded — is what proved the row shape was fine and
the deployed code was not.

  whoever matches, so a test invocation evaluates everyone. Today's window
  (09:30–noon CT) was chosen to miss the other testers' times: 09:00 Chicago and

  immediately misses it; wait until two minutes before the target.

## The stale-copy trap, twice in one day

This morning's rule — read a file back through PowerShell before deploying —
was written for **writes**. It cost another twenty minutes this afternoon
because it was not applied to **reads**.

My staged copy of the repo held 11 of the 33 screens and a `src/lib/shareMessage.js`
that was hours out of date. Reasoning from it produced two confident and wrong
claims: that nothing imported `dashboardPages.js` (it is imported by
`DashboardView.js:10`), and that a `boardDay` helper wrapping day numbers to
1-30 was committed at HEAD (it does not exist in the file at all). The second
one sent Gary chasing a contradiction that was never there.

**The rule, corrected:** re-stage a file from the laptop immediately before
reading it, not just before writing it. `git log -S` and `git diff --cached`
returning nothing for a symbol you can see in your copy means **your copy is
wrong**, not that git is hiding something — that is the tell, and it should
have stopped the second claim before it was made.
