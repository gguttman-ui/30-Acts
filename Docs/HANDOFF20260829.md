## This afternoon: getting it onto a phone

Everything changed is JavaScript. No new native modules. So an **OTA update is
enough** — no new build needed, for Gary or for David.

```powershell
cd 'C:\Users\Gary laptop\Documents\30-Acts-current'
npx expo export --platform ios
git add -A
git commit -m 'Consistent share row across all screens'
git push origin main
eas update --branch preview --message 'Consistent share row across all screens'
```

`npx expo export` is the real check — it surfaces bundle errors the parse check
cannot. Run it before pushing the update.

On the phone: open the app **twice**. First launch downloads the update, second
applies it.

**Then check the Settings build stamp before judging anything.** If it says
"update embedded," the OTA never applied and you are looking at the old version.
This has wasted time before.

If a full rebuild is wanted instead:
`eas build --profile preview --platform ios` — and delete the old app off the
iPhone first, or iOS keeps running the previous version.

## Admin page — growth metrics (added, needs one SQL step)

Four tiles added to the Admin dashboard in a new "📈 Growth" card, below the
existing Overview card. They show a dash until there is data, so they can ship
now and fill in on their own after launch.

| Tile | Where the number comes from |
|---|---|
| Downloads | **App Store Connect only.** Entered by hand — see below. |
| Signed in | `auth.users` where `last_sign_in_at` is not null |
| Did 1+ act | distinct `user_phone` in `completions` |
| 30 days in a row | consecutive-date run of 30+ in `completions.local_date` |

**Downloads cannot be queried.** Nothing in Supabase can see App Store install
counts — that number lives in App Store Connect and no query will ever produce
it. So it is stored in a new `app_metrics` table and updated manually:

```sql
UPDATE public.app_metrics SET value = 1234, updated_at = now()
WHERE key = 'downloads';
```

The "30 days in a row" count is a real streak — consecutive calendar dates —
not merely "30 acts logged."

**SQL step: DONE.** `growth-metrics.sql` was run on 2026-08-29. `app_metrics`
and `admin_growth_stats()` exist and are verified working. The existing
`admin_dashboard_stats()` was not touched, so the Overview tiles are unaffected.

The function's admin guard was amended to `session_user <> 'postgres' AND NOT
EXISTS (...)`, which lets it be called from the Supabase SQL Editor (no user JWT
there) while still blocking non-admin app users.

Verified return: `{"downloads":1234,"signins":11,"did_one_act":9,"streak_30":2}`
— see the pre-launch section below, all of that is test data.

**If the tiles show dashes in the app,** the admin guard is the first thing to
check: it matches `admins.email` against the JWT email. If
`admin_dashboard_stats()` guards itself differently, copy that guard.

  **Decide before launch:** either delete test completions out of production, or

  data is better if those rows have no further use; filtering is better if the
  seeded accounts are still needed for testing.
  Query to see who they are:

  ```sql
  WITH d AS (
    SELECT DISTINCT user_phone, local_date::date AS ld
    FROM public.completions
    WHERE user_phone IS NOT NULL AND local_date IS NOT NULL),
  g AS (
    SELECT user_phone, ld,
           ld - (row_number() OVER (PARTITION BY user_phone ORDER BY ld))::int AS grp
    FROM d),
  runs AS (
    SELECT user_phone, grp, count(*) AS run_len, min(ld) AS started, max(ld) AS ended
    FROM g GROUP BY user_phone, grp)
  SELECT user_phone, run_len, started, ended
  FROM runs WHERE run_len >= 30 ORDER BY run_len DESC;
  ```

## Things that keep costing time — worth remembering

- **Check the build stamp first**, every time a change appears not to have taken
  effect. `v<runtime> · <channel> · update <id>` in Settings.
- **PowerShell eats `$`** inside double-quoted arguments. Use single quotes for
  any message containing one.
- **Facebook cannot be tested in Expo Go.** Dev or TestFlight/preview build only.
  A failure there proves nothing.
- **TestFlight and the App Store share one binary and one channel.** A
  `production` update reaches real users with no gate. Test on `preview` first.
- **`HistoryScreen.js` contains `DayDetailScreen`**, and it is a different file
  from `DailyActScreen.js`. They have separate share code. Fixing one has never
  affected the other. Test both.
