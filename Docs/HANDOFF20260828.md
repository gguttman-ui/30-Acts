### Dashboard streak pages — final rules
Chronological, left → right:

| What | Where it goes |
|---|---|
| Short streaks that never reached 30 | **Packed together** on a shared `EARLIER STREAKS` page — oldest first, one blank tile between streaks, 30 tiles per page |
| A completed 30-day streak | **Its own page**, `STREAK · Completed · <start>–<end>` |
| Days past 30 | **A further page**, filling slots 1, 2, … of a fresh 30-slot board, `STREAK · LAP 2 · <dates>` |
| Today | The interactive board on the far right, with the **+** tile |

Verified against six short May/June streaks (2, 3, 1, 5, 4, 7 days) followed by a 32-day streak: page 1 is `EARLIER STREAKS` with 27 slots (22 acts + 5 separators), page 2 the completed 30, page 3 days 31–32 in slots 1 and 2, page 4 today.

**Bug found in passing:** a partial second lap rendered as *today's live board*, **+** tile and all, even when the streak had died months earlier — an abandoned 32-day streak looked like it was still running. It now checks that the last act was today or yesterday before treating a lap as live.

**Also fixed:** today's tile printed its date instead of **TODAY** whenever its page was read-only. That happens exactly when day 30 lands today, since completing the lap flips the whole page to read-only. The TODAY label no longer depends on the tile being interactive.

### Venmo — the white screen
**Cause:** the button opened `https://venmo.com/u/Actsofkindness30` in Safari. That profile page is login-walled and renders blank on mobile, which reads as a broken app.

**Fix:** both the Donate screen and the bracelet payment screen open the Venmo app's pay sheet via `venmo://paycharge?txn=pay&recipients=Actsofkindness30`, falling back to the web link only when Venmo is not installed. The bracelet screen also prefills **amount = 6.95** and a "Kindness bracelet shipping" note.

Uses `Linking.openURL`, **not** `canOpenURL` — the latter returns false for any scheme not whitelisted in `Info.plist`, which would have forced a native build. `openURL` just rejects if the app is missing, and that is caught. This is why the fix shipped over the air.

### Reminder card — rebuilt
Ended up quite different from where it started:

- **One control per reminder.** The `● ON` / `○ OFF` button toggles *and* saves in the same tap. The Set buttons are gone; time changes auto-save 1.2 seconds after you stop tapping the arrows.
- **Reminder 1 has its own flag.** It used to share `reminderEnabled` with the master switch, so switching reminders on switched slot 1 on at the same instant — you never got to choose. Master now means "texts allowed at all"; slot 1 is scheduled separately, off by default.
- **Reminder 2 requires reminder 1.** Its control is inert and dimmed until slot 1 is on, `toggleReminder` refuses it in logic as well as UI, and switching slot 1 off switches slot 2 off with it.
- **Master off clears both slots**, so switching it back on starts from OFF/OFF instead of silently resuming an old schedule.
- **First visit lands OFF.** The old load only applied the stored value when it was already a boolean, so a new user fell through to whatever the initial state happened to be. Now an explicit `=== true` check — nobody is opted into texts by default.
- **Confirmation banner**, 5 seconds, pinned under the Settings header.

**Why the banner took four attempts** — worth recording, because each failure looked identical from the phone:

1. It fired only from the status chip, not from the switches actually being used.
2. It fired only *after* `await handleSave(...)` succeeded, so any stall or throw inside that function — it contains an unguarded call to the moderation API — swallowed it. It now fires the instant you tap, before any network work, and a failed save corrects it afterwards.
3. Its state could be wiped by a re-mount triggered by the save itself. The message now lives at module scope and a fresh mount picks it up mid-flash.
4. **The actual cause:** it rendered *inside* the Daily Reminder card. Tapping a control near the bottom of a long card put the banner hundreds of pixels above the fold. Ten seconds of an invisible banner looks exactly like no banner. It now sits outside the ScrollView, directly under the header.

### Feedback — multiple submissions a day
Confirmed working. RLS was never the problem (`Anyone can insert feedback`, `with_check: true`). Two causes:

- Submit was disabled whenever `msg.length < 10`, and on a return visit the screen kept its old state, so the gate could sit stuck no matter what you typed. Validation moved into the press handler — the button is always tappable and says why it refused.
- The thank-you screen bounced back to Settings after 3 seconds. It now offers **Send more feedback**, which clears the form in place.

Errors now include the Postgres code, so a server-side block would name itself (`23505` unique violation, `42501` RLS refusal) instead of hiding behind "please try again."

### Build stamp
Bottom of Settings: `v1.0.0 · production · update <id>`. Added mid-session and immediately earned its place — it is how we established that the phone *was* running the latest bundle, which redirected the whole flash hunt from delivery to rendering. **Check it first whenever a change "isn't working."** `update embedded` means no OTA has ever applied to that device.

## New: `Docs/RELEASE-WORKFLOW.md`

Covers the sandbox question. The short version:

**TestFlight and the App Store serve the same binary**, and a build's channel is fixed at build time. Build 96 listens to `production`, and the store release will be that same build on that same channel — so once live, `eas update --branch production` reaches real users with nothing in between.

The `preview` channel in `eas.json` is the sandbox: publish there, verify on a tester phone, then promote the same commit to `production`. Once there are real users, ramp with `--rollout-percentage` and keep `eas update:rollback` ready — and rehearse that command once before you need it.

**The bigger gap is Supabase.** One project serves testers and real users alike, so tester data lands in production tables and a schema experiment hits everyone. A staging project is the real fix and is a deliberate decision, not a five-minute one.

## Gotchas worth keeping

- **PowerShell eats `$`.** In double quotes, `$6.95` becomes `.95`, and it killed one `eas update` outright. **Single-quote** any message containing a `$`.
- **Force-close twice.** First launch downloads an update, second applies it.
- **Delete the old app** before installing a new preview build. Does not apply to OTA.
- **TikTok needs All Photos** — iPhone Settings → TikTok → Photos → All Photos, or it cannot see the saved card.
- **Facebook "spinner on Post"** is Facebook-side. Close and reopen FB, confirm login, retry. The picture is safe in Photos.
